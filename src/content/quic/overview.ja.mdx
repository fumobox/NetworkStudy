## なぜ QUIC か

TCP の上の HTTP/2 には 2 つの負担がある。接続を開くのに TCP と TLS のハンドシェイクが要り（最初の要求までに 2 往復）、パケットが 1 つ失われるとすべてのストリームが止まる。**QUIC** は UDP の上で動くトランスポートのプロトコルで、この両方を解決する。**HTTP/3** は QUIC の上で HTTP を運ぶ。

## TLS を組み込んだ 1 往復

QUIC には独立した TLS の層がなく、TLS 1.3 のメッセージは QUIC の `CRYPTO` フレームで運ぶ。1 往復で接続ができ、鍵もそろうので、ブラウザーは `Finished` と一緒に要求を送る。

ハンドシェイクが進むにつれ、パケットは違う**暗号化レベル**で保護される。

| パケット | 鍵 | 運ぶもの |
|---|---|---|
| `Initial` | 接続 ID から作るので、誰でも計算できる | ClientHello、ServerHello |
| `Handshake` | TLS の鍵交換から作る | 残りの TLS のハンドシェイク |
| `0-RTT` | 前の訪問のセッションチケットから作る | 早期の要求 |
| `1-RTT` | アプリケーションの鍵 | HTTP/3 の要求と応答 |

レベルの違うパケットを、1 つの UDP データグラムにまとめられる。パケット番号は、Initial、Handshake、アプリケーションのデータ（0-RTT と 1-RTT で共有）の 3 つの**パケット番号の空間**で別々に数える。空間の中でパケット番号は使い回さない。

## 0-RTT

ブラウザーが以前接続していてセッションチケットを持っていれば、最初のデータグラムで要求を送れる（**0-RTT**）。サーバーはそれを受け付けてすぐに答えることも、断ることもできる。断られたら、ブラウザーはハンドシェイクのあとで要求を送り直す。攻撃者は 0-RTT のデータを記録してもう一度送れる（リプレイ）ので、繰り返しても問題のない要求だけに使う。

## ストリームとロス

HTTP/3 の要求はそれぞれ別の QUIC の**ストリーム**を使い、QUIC はストリームごとに別々に渡す。パケットが失われて止まるのは、そのパケットがデータを運んでいたストリームだけ。QUIC は、後に送ったパケットが確認応答されたとき（ステップ実行では 3 つ大きい番号）にロスとみなす。確認応答がまったく来なければ、プローブタイムアウト（PTO）のあとで送り直す。どちらも**データ**を新しい番号の新しいパケットで送り直す。

## ステップ実行で見てほしいところ

- 各パケットのラベル。種類、パケット番号、中のフレーム（全体はパケットの詳細の Frames の欄）。
- **送ったパケット番号**の表。3 つの別々の空間と、Initial と Handshake の空間を捨てるところ。
- 「もしも…」のオプションで、0-RTT が受け付けられる場合と断られる場合、最初のデータグラムのロス（PTO）、ストリーム 0 のパケットのロス（ストリーム 4 は止まらない）。

## 手元で試す

```sh
curl -sI https://www.cloudflare.com/ | grep -i '^alt-svc'
```

出力（macOS 26、2026-09-29）:

```
$ curl -sI https://www.cloudflare.com/ | grep -i '^alt-svc'
alt-svc: h3=":443"; ma=86400
```

- 最初のリクエストは TCP で行く。`alt-svc` のヘッダーは、同じサイトが UDP の 443 番ポートで HTTP/3（`h3`）も話すこと、ブラウザーがそれを 1 日（`ma=86400`）覚えてよいことを知らせる。次の接続では QUIC を使える。
- macOS に入っている curl は HTTP/3 なしで作られている。HTTP/3 付きで作った curl なら `curl --http3 -sI https://www.cloudflare.com/` を試せる。ブラウザーでは、Network のパネルの Protocol の列に `h3` と出る。Wireshark では、表示フィルター `quic` で QUIC のパケットが見える。TLS と同じく、中身は暗号化されている。

## このページについて

1 つのメッセージを 1 つの QUIC パケットとして描き、パケットが同じデータグラムに入るときは説明で示した。Retry、バージョンの交渉、ヘッダーの保護、接続の移行、鍵の更新、輻輳制御、サーバーによる Handshake パケットの確認応答、HTTP/3 の制御ストリームと QPACK は省いた。ブラウザーはサーバーが HTTP/3 に対応していることを `Alt-Svc` ヘッダーや DNS のレコードで知るが、それは描いていない。パケットの大きさは例。
