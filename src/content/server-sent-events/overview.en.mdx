## Events from the server over plain HTTP

Some pages need to hear from the server without asking again and again: prices, notifications, a build log. **Server-Sent Events** (SSE) do this with one ordinary HTTP request whose response never ends. The page writes:

```js
const source = new EventSource('/events')
source.onmessage = (event) => { … }
source.addEventListener('price', (event) => { … })
```

The browser sends a GET, and the server keeps the response open and writes an event whenever it has one. Unlike [WebSocket](/themes/websocket), the channel goes one way only, from the server to the page; the page still uses ordinary requests to send anything back. `EventSource` only does GET and cannot add custom headers, so some APIs (for example those that stream AI chat responses) use the same `text/event-stream` format but read it with `fetch()`, which lets them POST.

## The text/event-stream format

The response is UTF-8 text made of lines. Each event is a few lines ended by a blank line:

| Line | Meaning |
|---|---|
| `data: …` | The payload. Several data lines are joined with a line feed |
| `event: price` | The event type (default `message`) |
| `id: 42` | The last event ID, used when reconnecting |
| `retry: 5000` | How long to wait before reconnecting, in ms |
| `: anything` | A comment, ignored |
| (blank line) | Ends the event and fires it (if it has data) |

Lines can end with CRLF, LF or CR.

## How the browser reads a stream

The HTML Standard spells out the algorithm exactly:

- The field is the text before the first colon, and the value the text after it, with **one** leading space removed.
- `data` lines are joined with a line feed, and the final line feed is removed.
- An event without `event:` has the type `message` and goes to `onmessage`.
- `id` stays in effect until the server sends another one. An `id` line with no value resets it to empty.
- `retry` is used only if it is all digits.
- An event that is not followed by a blank line when the stream ends is discarded.

```
data: first event
id: 1

data:  third event

```

The second event's data is `" third event"`, with one space left.

## A response that does not end

The server answers `200` with `Content-Type: text/event-stream` and no `Content-Length`, because the length is not known. In HTTP/1.1 the body is usually sent with **chunked** transfer coding: each chunk starts with its size in hexadecimal, and a chunk of size `0` ends the response (RFC 9112 §7.1). A response that stops without that last chunk is incomplete (§8). Without chunked and without `Content-Length`, the body simply runs until the connection closes (§6.3). In HTTP/2 the body travels in DATA frames on a stream that simply does not end; chunked does not exist there.

The HTML Standard warns that chunking can hurt the reliability of the stream if it is done by a layer that does not know the timing of the events (it can then be turned off), and suggests a comment line every 15 seconds or so, because some older proxies drop connections that stay idle.

## readyState and reconnection

| readyState | Meaning |
|---|---|
| `CONNECTING` (0) | Connecting, or waiting to reconnect |
| `OPEN` (1) | Receiving events |
| `CLOSED` (2) | Given up, or closed by the page |

When the connection drops, or even when the server ends the response normally, the browser **reconnects on its own**. It sets readyState to `CONNECTING`, fires `error`, waits the reconnection time (from `retry:`, or a default of a few seconds; it may wait longer), and sends the GET again. If the last event ID is not empty, it adds a `Last-Event-ID` header with it. What the server does with that header is up to the application: a server that keeps recent events can send everything after that ID, so the page misses nothing.

## When the browser gives up

The browser **fails** the connection, sets readyState to `CLOSED`, fires `error`, and never reconnects when:

- the status is anything other than 200. `204 No Content` is the standard way for a server to say "stop";
- the `Content-Type` is not `text/event-stream`, for example when a misconfigured route returns an HTML page.

The page can also stop it with `source.close()`: readyState becomes `CLOSED` at once, no `error` fires, and the browser does not reconnect.

A network error or the end of the response only makes it reconnect. In `onerror`, check `readyState`: `CONNECTING` means the browser is retrying, `CLOSED` means the page has to create a new `EventSource` if it wants one.

## Six tabs, HTTP/1.1 and HTTP/2

Over HTTP/1.1 each open `EventSource` keeps one connection busy for as long as it lives. Browsers typically allow about six HTTP/1.1 connections at a time to one server, shared by all tabs. That is browser behaviour, not a standard: RFC 9112 §9.4 sets no number, though the older RFC 2616 said 2. With six tabs of the same site open, every connection is taken, and the next request, even for an image, has to wait. The HTML Standard warns about this and suggests a separate domain name per connection, letting the user turn the stream on or off on each page, or sharing one `EventSource` through a shared worker.

HTTP/2 avoids the problem: each `EventSource` is just one stream on a single connection, and servers commonly allow 100 or more streams at once (RFC 9113 §6.5.2 recommends at least 100).

## Proxies and buffering

SSE is ordinary HTTP, so it passes through proxies that would block a WebSocket's Upgrade. But a proxy that **buffers** responses holds the events back and delivers them late, in batches. nginx, for example, buffers proxied responses by default; its `proxy_buffering off` setting, or an `X-Accel-Buffering: no` response header from the application, turns that off. Send `Cache-Control: no-store` so that no cache keeps the stream.

## SSE or WebSocket

| | SSE | WebSocket |
|---|---|---|
| Direction | Server → browser | Both ways |
| Data | UTF-8 text | Text or binary |
| On the wire | One long HTTP response | Upgrade (101, HTTP/1.1), then frames |
| Reconnect | Built in (`retry`, `Last-Event-ID`) | Up to the page |
| Proxies | Plain HTTP (may buffer) | Must pass the Upgrade |

## What to look for in the walkthrough

- The **Events fired at the page** table, the **Last event ID string** and the **Reconnection time**.
- The chunk sizes and the lines of each event.
- In the "What if…" options:
  - a dropped connection, the `retry` wait, `Last-Event-ID: 2` and the replayed events 3 and 4;
  - `204` and a wrong `Content-Type` leading to `CLOSED`;
  - the `queued` request with six HTTP/1.1 tabs;
  - streams 1 to 13 on one HTTP/2 connection.

## About this page

- TCP and TLS are assumed to be set up, and HTTP is shown unencrypted so that it can be read (in practice it is https). Only TCP's FIN is drawn.
- Each chunk is drawn as one message, and chunks line up with events. In practice they need not; the parser handles that.
- `retry: 5000` is an example value sent by the server, and the browser's extra wait (backoff) is not drawn.
- The server keeps its recent events so that it can send them again. Six tabs are shown as rows of a table.
- Headers such as User-Agent and Cookie are left out. The 100 streams and the 15 seconds are example values.
- In HTTP/2, the connection preface, SETTINGS ACK, WINDOW_UPDATE and HPACK are left out.
