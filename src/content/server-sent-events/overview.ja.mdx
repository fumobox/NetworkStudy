## HTTP のままでサーバーから送る

株価、通知、ビルドのログのように、何度も問い合わせずにサーバーからの知らせを受けたいページがある。**Server-Sent Events**（SSE）は、応答が終わらない普通の HTTP の要求 1 つでこれを行う。ページはこう書く。

```js
const source = new EventSource('/events')
source.onmessage = (event) => { … }
source.addEventListener('price', (event) => { … })
```

ブラウザーは GET を送り、サーバーは応答を開いたままにして、イベントがあるたびに書き込む。[WebSocket](/themes/websocket) と違い、通り道はサーバーからページへの片方向だけ。ページから何かを送るには、普通の要求を使う。`EventSource` は GET しか使えず、独自のヘッダーも付けられない。そのため、同じ `text/event-stream` の形式を使いながら、POST できる `fetch()` で読む API もある（例えば AI のチャットの応答を流すもの）。

## text/event-stream の形式

応答は UTF-8 の文字列で、行が並ぶ。1 つのイベントは、空行で終わるいくつかの行。

| 行 | 意味 |
|---|---|
| `data: …` | 中身。data の行が複数あれば改行でつなぐ |
| `event: price` | イベントの種類（なければ `message`） |
| `id: 42` | 最後のイベント ID。再接続で使う |
| `retry: 5000` | 再接続までの待ち時間（ミリ秒） |
| `: 何でも` | コメント。無視される |
| （空行） | イベントを終えて発火する |

行の終わりは CRLF、LF、CR のどれでもよい。

## ブラウザーの読み方

HTML Standard は手順を細かく決めている。

- 最初のコロンより前がフィールド名、後が値。値の先頭の空白は **1 つだけ**除く。
- `data` の行は改行でつなぎ、最後の改行を除く。
- `event:` のないイベントの種類は `message` で、`onmessage` に届く。
- `id` は、サーバーが次の値を送るまで有効。値のない `id` の行で空に戻る。
- `retry` は、すべて数字のときだけ使う。
- ストリームが終わったとき、空行で終わっていないイベントは捨てる。

```
data: first event
id: 1

data:  third event

```

2 つ目のイベントの data は `" third event"` で、空白が 1 つ残る。

## 終わらない応答

サーバーは `Content-Type: text/event-stream` の `200` で答え、長さがわからないので `Content-Length` は付けない。HTTP/1.1 では本文を **chunked** の転送コーディングで送る。各チャンクは 16 進のサイズで始まり、サイズ `0` のチャンクで応答が終わる（RFC 9112 §7.1）。最後のチャンクなしに止まった応答は不完全（§8）。HTTP/2 では、本文は終わらないストリームの DATA のフレームで運ぶ。そこに chunked はない。

HTML Standard は、イベントの時間の要求を知らない層がチャンクに分けると、ストリームの信頼性を損ねることがある（そのときはチャンクを止められる）と注意している。また、古いプロキシには何も流れない接続を切るものがあるので、15 秒ほどごとにコメントの行を送るよう勧めている。

## readyState と再接続

| readyState | 意味 |
|---|---|
| `CONNECTING`（0） | 接続中、または再接続を待っている |
| `OPEN`（1） | イベントを受け取っている |
| `CLOSED`（2） | あきらめた、またはページが閉じた |

接続が切れたとき、そしてサーバーが応答を普通に終えたときでも、ブラウザーは **自分で接続し直す**。readyState を `CONNECTING` にして `error` を発火し、再接続の待ち時間（`retry:` で決まる。なければ数秒の既定の値。もっと待ってもよい）を待って、GET を送り直す。`id` を受け取っていれば、その値の `Last-Event-ID` ヘッダーを付ける。サーバーがこのヘッダーをどう使うかはアプリケーションが決める。最近のイベントを保存しているサーバーなら、その ID より後をすべて送れるので、ページは何も取りこぼさない。

## ブラウザーがあきらめるとき

次のとき、ブラウザーは接続を **失敗**にし、readyState を `CLOSED` にして `error` を発火し、二度と接続し直さない。

- 状態コードが 200 以外のとき。サーバーが「止めて」と伝える標準の方法は `204 No Content`。
- `Content-Type` が `text/event-stream` でないとき。例えば、設定を誤った URL が HTML のページを返したとき。
- ページが `source.close()` を呼んだとき。

ネットワークのエラーや応答の終わりでは、接続し直すだけ。`onerror` では `readyState` を確かめる。`CONNECTING` ならブラウザーが試し直していて、`CLOSED` なら、続けたければページが新しい `EventSource` を作る。

## 6 つのタブ、HTTP/1.1 と HTTP/2

HTTP/1.1 では、開いている `EventSource` はそれぞれ、生きているあいだ接続を 1 本ふさぐ。ブラウザーはふつう、1 つのサーバーへの HTTP/1.1 の接続を同時に約 6 本までにし、それをすべてのタブで分け合う。これはブラウザーの動きで、標準ではない。RFC 9112 §9.4 は数を決めていない（以前の RFC 2616 は 2 本としていた）。同じサイトを 6 つのタブで開くと接続はすべてふさがり、次の要求は、画像でも待たされる。HTML Standard はこのことを注意し、接続ごとに別のドメイン名を使う、ページごとにストリームを入れたり切ったりできるようにする、共有ワーカーで 1 つの `EventSource` を分け合う、といった対策を挙げている。

HTTP/2 ならこの問題は起きない。`EventSource` はそれぞれ 1 本の接続の中のストリーム 1 つにすぎず、サーバーはふつう同時に 100 本以上のストリームを許す（RFC 9113 §6.5.2 は 100 以上を勧める）。

## プロキシとバッファリング

SSE は普通の HTTP なので、WebSocket の Upgrade を止めてしまうプロキシも通る。ただし、応答を **バッファリング**するプロキシはイベントをためこみ、遅れてまとめて届ける。例えば nginx は、中継する応答を既定でバッファリングする。`proxy_buffering off` の設定や、アプリケーションが返す `X-Accel-Buffering: no` の応答ヘッダーで止められる。キャッシュがストリームを持たないよう、`Cache-Control: no-store` を付ける。

## SSE と WebSocket

| | SSE | WebSocket |
|---|---|---|
| 向き | サーバー → ブラウザー | 双方向 |
| データ | UTF-8 のテキスト | テキストかバイナリー |
| 通信路の上 | 1 つの長い HTTP の応答 | Upgrade（101）の後にフレーム |
| 再接続 | 組み込み（`retry`、`Last-Event-ID`） | ページの仕事 |
| プロキシ | 普通の HTTP（ためこまれうる） | Upgrade を通す必要がある |

## ウォークスルーで見るところ

- **ページに届いたイベント** の表、**最後のイベント ID**、**再接続の待ち時間**。
- チャンクのサイズと、各イベントの行。
- 「もしも…」の選択肢:
  - 切れた接続、`retry` の待ち、`Last-Event-ID: 2` と、送り直されるイベント 3 と 4。
  - `204` と誤った `Content-Type` で `CLOSED` になること。
  - HTTP/1.1 の 6 つのタブで待たされる要求（`queued`）。
  - 1 本の HTTP/2 の接続の中のストリーム 1〜13。

## このページについて

- TCP と TLS の接続はできているものとし、HTTP は読めるよう暗号化せずに描く（実際は https）。TCP は FIN だけを描く。
- 1 つのチャンクを 1 つのメッセージとして描き、チャンクとイベントの区切りをそろえる。実際はそろわなくてよく、解析の手順はそれを扱う。
- `retry: 5000` はサーバーが送る例の値で、ブラウザーの追加の待ち（間隔を広げること）は描かない。
- サーバーは送り直せるよう、最近のイベントを保存している。6 つのタブは表の行で示す。
- HTTP/2 では、接続の序文、SETTINGS の ACK、WINDOW_UPDATE、HPACK を省く。
