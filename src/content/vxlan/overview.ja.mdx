## なぜオーバーレイか

[ブリッジ](/themes/container-networking)は、1 台のホストの中のコンテナーや VM を LAN につなぐ。しかしコンテナーや VM は多くのホストで動き、ホスト同士はふつう、1 台の大きなスイッチではなく、経路制御の IP ネットワークでつながっている。1 つの [VLAN](/themes/vlan) をすべてのラックに広げるのはもろく、VLAN ID は 12 ビットで 4094 のセグメントしか作れない。データセンターのテナントがそれぞれ自分のネットワークを欲しがると、足りない。

**オーバーレイ**は、代わりに IP ネットワークの上に LAN を作る。各ホストは、コンテナーの Ethernet のフレームを UDP で包み、ふつうの IP ネットワーク（**アンダーレイ**）で正しいホストに送り、受け取ったホストが包みを解く。コンテナーには 1 つの LAN が見え、アンダーレイにはホストの間の UDP のパケットが見える。これを行ういちばん広く使われている方法が **VXLAN**（RFC 7348）。

## VXLAN のパケット: フレームを包む 50 バイト

VXLAN のパケットは、内側の Ethernet のフレーム全体の前に、3 つのヘッダーを付けたもの。

- **VXLAN のヘッダー**（8 バイト）。フラグのバイト（`I` = `0x08`。VNI が有効という意味）、予約のビット、**24 ビットの VNI**（VXLAN Network Identifier）、予約のバイト。
- **UDP のヘッダー**。宛先ポートは、IANA が VXLAN に割り当てた **4789**。
- **外側の IP のヘッダー**。送るホストから受け取るホストへ。

外側が IPv4 なら、内側の IP パケットに 50 バイトが加わる。内側の Ethernet のヘッダー（14）、VXLAN（8）、UDP（8）、外側の IP（20）。外側が IPv6 なら 70 バイト。24 ビットの VNI で、約 1,600 万のセグメントを作れる。

RFC 7348 は、UDP のチェックサムを 0 で送るべき（SHOULD）としている（外側が IPv4 のとき。IPv6 で UDP のチェックサムを 0 にできるのは、RFC 6935 と RFC 6936 の条件のもとだけ）。

## VTEP: トンネルのポートを持つスイッチ

包んだり解いたりする機器が **VTEP**（VXLAN Tunnel End Point）。Linux では、ホストのブリッジにつながった VXLAN のネットワークデバイス。1 つだけ余分なポート（トンネル）を持つスイッチのようにふるまう。

- [スイッチ](/themes/switching)と同じく、自分のポートから自分のホストの MAC アドレスを学習する。
- VXLAN のパケットを受け取ると、内側の送信元の MAC アドレスが外側の送信元の IP アドレスの先にいると、VNI ごとに学習する（RFC 7348 §4.1）。
- 知っている MAC アドレス宛てのフレームは、1 つの VXLAN のパケットで、その VTEP に直接送る。

## ブロードキャストと知らない宛先

最初の ARP の要求のようなブロードキャストや、どの VTEP もまだ学習していない MAC アドレス宛てのフレームは、その VNI を持つすべてのホストに届けなければならない。やり方は 2 つある。

- **マルチキャスト**。VNI ごとに IP のマルチキャストグループを対応づけ、その VNI のすべての VTEP が参加する。送る側はグループに 1 つ送り、アンダーレイが複製する（RFC 7348 §4.2）。アンダーレイがマルチキャストの経路制御に対応している必要がある。
- **送信元での複製**（ヘッドエンドレプリケーション）。各 VTEP は、その VNI のほかの VTEP を**流す先の一覧**に持ち、それぞれに別々のユニキャストのコピーを送る（RFC 8365 は ingress replication と呼ぶ）。どんな IP ネットワークでも動き、送る側が手間を負う。

どちらでも、応答はユニキャスト。応答する VTEP は、送った側の居場所を学習したところだから。VTEP は、トンネルから来たパケットをトンネルに流し返さない（スプリットホライズン）。ほかの VTEP は、送った VTEP から直接コピーを受け取っているから。スイッチが、フレームを受け取ったポートに送り返さないのと同じ。

## VNI でテナントを分ける

VNI ごとに、別の L2 のセグメントになる。VNI 100 のブロードキャストは VNI 100 のポートと VTEP にだけ届き、受け取った VTEP も VNI 100 のポートにだけ渡す。そのため 2 つのテナントは、別々の VNI で同じアドレス（MAC アドレスでも）を使え、互いの通信を見ることはない。アンダーレイは気にしない。違いは VXLAN のヘッダーの数字 1 つだけ。

VXLAN 自身には暗号化も認証もない。アンダーレイに届く者は、フレームを読むことも、偽のフレームを VTEP に送ることもできる。アンダーレイを信頼できるものにするか、別の方法で守る必要がある。

## MTU: 50 バイトをどこかに収める

1500 バイトの内側のパケットは、1550 バイトの外側のパケットになる。RFC 7348 §4.3 は、VTEP は VXLAN のパケットを断片化してはならない（MUST NOT）とし、包んだフレームが収まるだけの MTU をアンダーレイに持たせることを推奨している。収める方法は 2 つ。

- アンダーレイの MTU を 1550 以上にする（例えば 9000 バイトのジャンボフレーム）。オーバーレイは MTU 1500 のままでよい。
- オーバーレイの MTU を 1450 に下げる。Linux は、下のデバイス（`dev`）を指定して作った VXLAN のデバイスにこの値（IPv6 なら − 70）を設定するが、コンテナーのインターフェースもこの値にする必要がある。

どちらもしないと、ウォークスルーのように、小さなパケットは通り、最大の大きさのものは消える。TCP のハンドシェイクは成功し、その後に接続が止まる。[パス MTU 探索](/themes/pmtud)と同じブラックホール。

RFC 7348 は、外側のヘッダーに DF（Don’t Fragment）ビットを立てるかどうかを決めていない。Linux の既定では立てない。そのときは、MTU の小さいアンダーレイのルーターが外側のパケットを断片化することがあり、受け取った VTEP はその断片を捨ててもよい（MAY）。DF を立てると、ルーターの ICMP のメッセージはコンテナーではなく、送った VTEP に届く。その後どうなるかは実装による。

## 送信元ポートと等コストの経路

データセンターのネットワークには、ふつう 2 台のホストの間に等コストの経路がいくつもあり、ルーターはヘッダーのハッシュでパケットごとに 1 つを選ぶ（ECMP）。2 台のホストの間の VXLAN のパケットは、どれも外側のアドレスと宛先ポートが同じ。すべて同じに見えると、ハッシュはすべての流れを 1 つの経路に載せてしまう。

そこで RFC 7348 §5 は、VTEP が外側の**送信元ポート**を内側のパケットのハッシュから作ることを勧めている（範囲は 49152〜65535）。内側の流れが違えば送信元ポートが違い、経路に散らばる。1 つの流れはいつも同じポートになり、1 つの経路にとどまって、順序が入れ替わらない。

## コントロールプレーン: 静的な表と EVPN

流して学習するやり方でも動くが、流すぶん無駄があり、VTEP は通信が届くまで学習できない。大きなネットワークでは、代わりに**コントロールプレーン**を使う。各 VTEP は、自分の先にある MAC アドレスと IP アドレスを告知する（例えば BGP で運ぶ EVPN の経路。RFC 8365、RFC 7432）。ほかの VTEP は、通信が始まる前に表に書く。IP アドレスもわかっていれば、VTEP は ARP の要求に自分で答えられる（代理 ARP。RFC 9161）。ブロードキャストのほとんどはアンダーレイを越えなくなる。

## VXLAN、NVGRE、Geneve

- **VXLAN**（RFC 7348）: Ethernet を UDP で包む。ポート 4789、24 ビットの VNI、8 バイトのヘッダー。広く使われているプロトコルを記した Informational の RFC で、標準化の過程（Standards Track）の RFC ではない。
- **NVGRE**（RFC 7637、Informational）: Ethernet を GRE で包む。24 ビットの VSID。UDP のポートがないのでルーターがハッシュに使えるものが少なく、そのために 8 ビットの FlowID を持つ。
- **Geneve**（RFC 8926、Standards Track）: UDP で包む。ポート 6081、24 ビットの VNI、中身の種類を示す Protocol Type（ふつうは Ethernet だが、それだけではない）、長さの変わるオプション。VXLAN が固定しているところを、広げられるように作られた。

## 標準か、実装か

- **RFC 7348**: ヘッダー、ポート 4789、学習、マルチキャストで流すこと、VTEP が断片化しないこと、送信元ポートの推奨の範囲。
- **Linux**:
  - 既定の宛先ポートは 8472（4789 が割り当てられる前に使われていた値）。標準のポートを使うには `dstport 4789` を指定する。
  - 外側の DF ビットは既定では立てない（`df`）。
  - 下のデバイスを指定して作った VXLAN のデバイスは、そのデバイスの MTU − 50 になる。
  - `srcport` を指定しないと、送信元ポートは `ip_local_port_range`（既定 32768〜60999）から選ぶ。
  - マルチキャストのパケットの TTL の既定は 1。
  - 送信元での複製は、転送の表の、MAC アドレスがすべて 0 の行を複数書いて表す。
- flannel や Docker のオーバーレイのドライバーのような**道具**は、その上で自分の既定を選ぶ。

## ウォークスルーで見るところ

- 各 VTEP の**転送の表**（FDB）。自分のポートと、相手の VTEP の IP アドレスの先にいる MAC アドレス。**流す先の一覧**（送信元での複製）と**近隣の表**（代理 ARP）も。
- 包んだパケットのフィールド。外側のアドレス、**TTL**（64、アンダーレイを通ると 63）、**Total Length**（内側の長さ + 50）、**UDP Dst** の 4789、8 バイトの **VXLAN** のヘッダー、**VNI**。
- 「もしも…」の選択肢:
  - マルチキャストグループに 1 つ送り、アンダーレイが複製する。
  - コントロールプレーンが埋めた表と、VTEP が答える ARP。
  - VNI 100 と 200 で同じアドレスを使う 2 つのテナント。
  - 収まらない 1500 バイトのパケット。
  - 2 つの流れが 2 つの別々の経路を通る。

## 手元で試す

Linux では、次のコマンドが VXLAN のデバイス（ここでは `vxlan100`）とその表の設定を読む。

```sh
ip -d link show type vxlan
bridge fdb show dev vxlan100
```

- `ip -d link show type vxlan` は、各デバイスの VNI（`id 100`）、自分のアドレス、宛先ポート（`dstport 4789`。指定しなければ 8472）、`nolearning` などのオプションを表示する。
- `bridge fdb show dev vxlan100` は転送の表を表示する。MAC アドレスと `dst`（相手の VTEP のアドレス）。MAC アドレスがすべて 0（`00:00:00:00:00:00`）の行が、送信元での複製の流す先の一覧。
- Wireshark では、表示フィルター `vxlan` で VNI と、中の Ethernet のフレームが見える。Wireshark は UDP のポート 4789 を既定で VXLAN として読む。Linux の古い既定の 8472 なら「Decode As」を使う。

## このページについて

- ホストは 2 台で、VTEP はそれぞれ 1 つ。VTEP のレーンは、ホストのブリッジと VXLAN のデバイスを合わせたもの。
- IPv4 だけ。アンダーレイは経路制御のネットワークを表す 1 つのレーンで、ECMP の選択肢の 2 つの経路は **Path** のフィールドにだけ表れる。
- 経路制御のプロトコル、PIM、IGMP のメッセージは描かず、転送の表の行は古くなっても消えない。
- 内側のフレームに VLAN のタグはなく、FCS とパディングは数えない。
- 送信元ポートと ECMP の経路は、Linux のものではなく説明用のハッシュで選ぶ。
- MTU の選択肢では、VTEP がフレームを捨て、何も返さない。実際の実装はさまざま。
- マルチキャストの選択肢では、VTEP の TTL は 1 より大きく設定してあるものとする。
- TCP のシーケンス番号は描かない。コントロールプレーンの行は最初のステップで示し、BGP は描かない。
