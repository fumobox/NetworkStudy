## Every link has a maximum size

Each link can carry IP packets only up to a certain size, its **MTU** (Maximum Transmission Unit). Ethernet’s is 1500 bytes. A PPPoE link, common for home fiber and DSL, adds 8 bytes of headers (PPPoE and PPP) inside the Ethernet frame, so its MTU is only **1492**. The smallest MTU along the whole route is the **path MTU**.

TCP’s **MSS** is announced in the SYN segments, and each side usually derives it from its own link: 1500 − 40 = 1460 (20 bytes of IP header and 20 bytes of TCP header). The MSS says nothing about the links in between.

## Path MTU discovery

With **path MTU discovery**, the sender sets the **DF** (Don’t Fragment) flag on every packet. A router that cannot forward a packet because the next link is too small drops it and sends back an ICMP **Destination Unreachable, code 4 (Fragmentation Needed)**. The message carries the **Next-Hop MTU** and the beginning of the dropped packet, so the sender can find the TCP connection it belongs to.

The sender records the smaller path MTU for that destination, and TCP resends the data in smaller segments (1492 − 40 = 1452 bytes). After about 10 minutes, the sender may try a larger size again.

## The black hole

If a firewall drops **all** ICMP, the Fragmentation Needed never arrives. Small packets such as the handshake get through, but every full-sized packet disappears, and the retransmissions are dropped too. The connection opens and then hangs: a **path MTU black hole**.

The fixes are to let ICMP type 3 code 4 through, to have the router rewrite the MSS in SYN segments (**MSS clamping**), or to have hosts probe the path themselves without relying on ICMP (**PLPMTUD**, RFC 4821 / RFC 8899).

## Fragmentation

Without DF, a router may split a packet into **fragments** instead. Each fragment gets its own IP header, the same **Identification**, a **Fragment offset** in units of 8 bytes, and the **MF** (More Fragments) flag on every fragment except the last. Only the destination puts them back together.

Fragmentation costs routers work, and losing any one fragment loses the whole packet, so TCP today avoids it with path MTU discovery. IPv6 routers never fragment: they send ICMPv6 **Packet Too Big** instead (RFC 8201), and every IPv6 link must carry at least 1280 bytes.

## What to look for in the walkthrough

- The packet with **DF** that the router drops, the **Next-Hop MTU** in the ICMP, and the PC’s path MTU and MSS going down.
- In “What if…”, a firewall that blocks the ICMP (the **black hole**) and a packet sent **without DF** (the router fragments it).

## Try it yourself

`ping -D` sets the Don’t Fragment bit, and `-s` sets the size of the data. 1472 bytes of data, plus 8 bytes of ICMP header and 20 of IPv4 header, make a 1500-byte packet:

```sh
ping -c 1 -D -s 1472 example.com
ping -c 1 -D -s 1473 example.com
```

Trimmed output (macOS 26, 2026-09-29):

```
$ ping -c 1 -D -s 1472 example.com
1 packets transmitted, 1 packets received, 0.0% packet loss
$ ping -c 1 -D -s 1473 example.com
1 packets transmitted, 0 packets received, 100.0% packet loss
```

- The 1500-byte packet gets through. The 1501-byte one does not even fit this computer’s own link (MTU 1500), and with DF set it may not be fragmented, so no reply comes back. On a path with a smaller link, such as a PPPoE line (1492), the limit would be lower, and a router could answer with an ICMP “fragmentation needed”.
- On Linux, the same test is `ping -M do -s 1472 example.com`, and `tracepath example.com` shows the path MTU hop by hop. In Wireshark, the display filter `icmp.type == 3 && icmp.code == 4` shows “fragmentation needed” messages.
