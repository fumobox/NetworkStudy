## What happens when you open a page

When you type `https://www.example.com/` into a browser, four protocols work one after another before the page appears. Each has its own theme on this site; this page puts them together in one walkthrough.

1. **DNS** — the browser asks a resolver for the IP address of `www.example.com`. See [DNS name resolution](/themes/dns-resolution).
2. **TCP** — the browser opens a connection to port 443 of that address with the three-way handshake. See [TCP three-way handshake](/themes/tcp-handshake).
3. **TLS** — over that connection, the browser and the server agree on keys, and the browser checks the server’s certificate chain. The request `GET /` is sent at the end, already encrypted. See [TLS 1.3 handshake and certificates](/themes/tls-handshake).
4. **HTTP** — the server answers with the page, encrypted with application traffic keys from the same handshake.

## Round trips add up

Before the first byte of the page arrives, the browser waits for several round trips: the DNS lookup (unless the answer is cached), one for TCP, one for TLS 1.3, and one more for the request and response themselves. This is why caching DNS answers and reusing connections make pages load faster.

## What to look for in the walkthrough

- The labeled bands in the diagram show which of the four stages each message belongs to.
- In the state panel, the browser keeps the result of each stage: the looked-up address, the TCP state, and the TLS state.
- The lock mark shows which messages are encrypted. Everything up to and including ServerHello, including the DNS lookup, is visible to anyone on the network.

The “What if…” options are left out on this page to keep it short. Try them in each theme.

## Try it yourself

`curl -v` prints each stage of opening a page:

```sh
curl -v -o /dev/null https://example.com/
```

Trimmed output (curl 8.7.1 on macOS 26, 2026-09-29):

```
* Host example.com:443 was resolved.
*   Trying [2606:4700:10::6814:179a]:443...
* Connected to example.com (2606:4700:10::6814:179a) port 443
* ALPN: curl offers h2,http/1.1
* SSL connection using TLSv1.3 / AEAD-CHACHA20-POLY1305-SHA256
* ALPN: server accepted h2
> GET / HTTP/2
< HTTP/2 200
```

- The lines follow the walkthrough: the name is resolved (DNS), a TCP connection is made, the TLS handshake agrees on TLS 1.3 and, through ALPN, on HTTP/2, and then the request and response go through the encrypted connection.
- To see how the round trips add up, ask curl for its timings, in seconds since the start:

```sh
curl -o /dev/null -s -w 'dns %{time_namelookup}  tcp %{time_connect}  tls %{time_appconnect}  first byte %{time_starttransfer}\n' https://example.com/
```

```
dns 0.001950  tcp 0.034158  tls 0.072933  first byte 0.131620
```

- Here the name came from a cache (2 ms). The TCP handshake took about one round trip (32 ms), TLS about one more (39 ms), and the first byte of the response one more after the request. Linux’s curl takes the same options.
