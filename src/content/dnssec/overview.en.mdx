## Why DNS needs signatures

Ordinary DNS has no way to prove that an answer is genuine. A resolver accepts the first response whose ID, ports and question match its query and that appears to come from the server it asked, so an attacker who guesses them, or who sits on the path, can hand out a forged address, and the resolver will cache it for everyone (see RFC 5452).

**DNSSEC** adds signatures to DNS data. It does not change how names are looked up (the root, .com and example.com still answer with referrals and records, as in the DNS theme), but every record set now comes with a signature that a **validating resolver** can check.

## Keys, signatures and the chain of trust

Each signed zone publishes its public keys as **DNSKEY** records, and signs each record set (**RRset**) with an **RRSIG** record. An RRSIG names the key that made it (the key tag and the zone) and is valid only between its inception and expiration times, so zones must be re-signed regularly.

A signature only helps if you trust the key, and that is where the parent comes in. The parent zone publishes a **DS** record for the child: a hash of the child’s key, signed with the parent’s own key. Many zones split this into two roles: a **key-signing key (KSK)** that signs only the DNSKEY set and is the one the DS points to, and a **zone-signing key (ZSK)** that signs everything else.

Starting from one key it trusts without proof, the root’s KSK configured as a **trust anchor**, the resolver can follow the links down: root key → DS for com. → com.’s key → DS for example.com. → example.com’s key → the RRSIG on the answer. This is the **chain of trust**.

## Secure, insecure, bogus

Here the result of validation is one of three (RFC 4035 also defines Indeterminate, for data with no trust anchor above it):

- **Secure**: every link was proven. The resolver sets the **AD** bit in its answer (if the query asked with AD or DO).
- **Insecure**: the parent proved that there is no signed delegation for the child (with signed NSEC or NSEC3 records), so the zone is simply not signed. The answer is ordinary DNS, without AD. Many names are still in unsigned zones.
- **Bogus**: validation failed where it should have succeeded, for example a signature is missing, wrong or expired. The resolver answers **SERVFAIL** instead of handing out the data, unless the query set **CD** (checking disabled): then the resolver returns the data without AD, and the client takes responsibility for validating it itself.

## What DNSSEC does not do

DNSSEC proves where data came from and that it was not changed, and it can prove that a name does not exist. It does **not** encrypt anything: anyone on the path can still read the questions and answers (DNS over TLS or HTTPS can hide them on the hop between your PC and the resolver). It also does not protect the last hop between your PC and the resolver, including the AD bit: your PC must validate itself, or that hop must be secured another way.

The keys, key tags and digests on this page are made up; IANA publishes the real root trust anchor.

## What to look for in the walkthrough

- The **chain of trust** table filling in: the DS from each parent, then the zone’s DNSKEY set, then the status.
- The **last signature check**, and the **AD** bit in the final answer.
- In “What if…”, an **unsigned** zone (Insecure), an answer **altered** on the way or **expired** signatures (Bogus, SERVFAIL), and a PC that sets **CD**.

## Try it yourself

`+dnssec` asks for the signatures too (the DO bit), here from a validating resolver:

```sh
dig @1.1.1.1 +dnssec cloudflare.com A
dig @1.1.1.1 cloudflare.com A
```

Trimmed output (macOS 26, 2026-09-30):

```
$ dig @1.1.1.1 +dnssec cloudflare.com A
;; flags: qr rd ra ad; QUERY: 1, ANSWER: 3, AUTHORITY: 0, ADDITIONAL: 1
; EDNS: version: 0, flags: do; udp: 1232
cloudflare.com.  107  IN  A      104.16.132.229
cloudflare.com.  107  IN  A      104.16.133.229
cloudflare.com.  107  IN  RRSIG  A 13 2 300 20261001062904 20260929042904 34505 cloudflare.com. …
$ dig @1.1.1.1 cloudflare.com A
;; flags: qr rd ra ad; QUERY: 1, ANSWER: 2, AUTHORITY: 0, ADDITIONAL: 1
; EDNS: version: 0, flags:; udp: 1232
```

- The `ad` flag means the resolver validated the answer: it followed the chain of trust from the root, as in the walkthrough. Without `+dnssec`, the EDNS flags have no `do`, and the RRSIG is left out. `ad` is still there, because dig sets the AD bit in its query by default (RFC 6840 §5.7); `+noadflag` turns that off.
- The RRSIG covers the A records: algorithm 13 (ECDSAP256SHA256), 2 labels, the original TTL 300, the expiration and the inception time (about two days apart here), the key tag 34505 of the DNSKEY that signed it, and the signer’s name.
- `dig +dnssec DNSKEY cloudflare.com` and `dig +dnssec DS cloudflare.com` show the keys and the delegation signer one level up. On Linux, `delv cloudflare.com` validates by itself and prints “fully validated”. In Wireshark, the filter `dns.flags.authenticated == 1` shows answers with `ad`.
