## Why DNS needs signatures

Ordinary DNS has no way to prove that an answer is genuine. A resolver accepts the first response whose ID and ports match its query, so an attacker who guesses them, or who sits on the path, can hand out a forged address, and the resolver will cache it for everyone (see RFC 5452).

**DNSSEC** adds signatures to DNS data. It does not change how names are looked up (the root, .com and example.com still answer with referrals and records, as in the DNS theme), but every record set now comes with a signature that a **validating resolver** can check.

## Keys, signatures and the chain of trust

Each signed zone publishes its public keys as **DNSKEY** records, and signs each record set (**RRset**) with an **RRSIG** record. An RRSIG names the key that made it (the key tag and the zone) and is valid only between its inception and expiration times, so zones must be re-signed regularly.

A signature only helps if you trust the key, and that is where the parent comes in. The parent zone publishes a **DS** record for the child: a hash of the child’s key, signed with the parent’s own key. By convention a zone has two keys: a **key-signing key (KSK)** that signs only the DNSKEY set and is the one the DS points to, and a **zone-signing key (ZSK)** that signs everything else.

Starting from one key it trusts without proof, the root’s KSK configured as a **trust anchor**, the resolver can follow the links down: root key → DS for com. → com.’s key → DS for example.com. → example.com’s key → the RRSIG on the answer. This is the **chain of trust**.

## Secure, insecure, bogus

The result of validation is one of:

- **Secure**: every link was proven. The resolver sets the **AD** bit in its answer (if the query asked with AD or DO).
- **Insecure**: the parent proved that the child has no DS (with a signed NSEC or NSEC3 record), so the zone is simply not signed. The answer is ordinary DNS, without AD. Many names are still in unsigned zones.
- **Bogus**: a signature is missing, wrong or expired where one was expected. The resolver answers **SERVFAIL** instead of handing out the data, unless the query set **CD** (checking disabled), in which case the client takes responsibility for validating it itself.

## What DNSSEC does not do

DNSSEC proves where data came from and that it was not changed, and it can prove that a name does not exist. It does **not** encrypt anything: anyone on the path can still read the questions and answers (DNS over TLS or HTTPS can hide them). It also does not protect the last hop between your PC and the resolver, unless your PC validates itself or that hop is protected.

The keys, key tags and digests on this page are made up; IANA publishes the real root trust anchor.

## What to look for in the walkthrough

- The **chain of trust** table filling in: the DS from each parent, then the zone’s DNSKEY set, then the status.
- The **last signature check**, and the **AD** bit in the final answer.
- In “What if…”, an **unsigned** zone (Insecure), an answer **altered** on the way or **expired** signatures (Bogus, SERVFAIL), and a PC that sets **CD**.
