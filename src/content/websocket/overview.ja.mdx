## なぜ WebSocket か

HTTP では、クライアントが頼み、サーバーが答える。チャットや、刻々と変わる画面や、ゲームでは、何か起きたときにサーバーから送りたい。WebSocket の前は、ページはそれを要求でまねていた。

| やり方 | 誰が送れるか | 接続 | 1 つのメッセージの負担 |
|---|---|---|---|
| ポーリング | クライアントが数秒ごとに聞く | 毎回の要求 | HTTP の要求 1 つ分。何もないことも多い |
| ロングポーリング | 知らせがあるまでサーバーが要求を保つ | 答えのたびに新しい要求 | メッセージごとに HTTP の要求 1 つ分 |
| [Server-Sent Events](/themes/server-sent-events) | サーバーだけ（流し続ける） | 終わらない 1 つの HTTP の応答 | 数バイト。ただし一方向だけ |
| **WebSocket** | 両方がいつでも | 開いたままの 1 つの接続 | 2〜14 バイトのヘッダー |

## 開始のハンドシェイク

WebSocket の接続は、`Upgrade: websocket` と `Connection: Upgrade`、乱数の `Sec-WebSocket-Key`、`Sec-WebSocket-Version: 13`、ページの `Origin` を付けた、ふつうの HTTP/1.1 の GET から始まる。サーバーは **101 Switching Protocols** で応じ、それからは同じ TCP の接続で、HTTP の代わりに WebSocket のフレームを運ぶ。ほかのステータスは失敗を意味する。

サーバーは、要求を理解したことを `Sec-WebSocket-Accept` の計算で示す。

```
dGhlIHNhbXBsZSBub25jZQ==                    Sec-WebSocket-Key（文字列のまま）
+ 258EAFA5-E914-47DA-95CA-C5AB0DC85B11      決まった GUID
→ SHA-1 → base64 = s3pPLMBiTxaQ9kYGzzhZRbK+xOo=
```

ブラウザーも同じ計算をし、値が違えば接続を失敗にする。これは認証ではない。サーバーが WebSocket を話せること、だまされて答えた HTTP のサーバーではないことを示すだけ。`ws://` は 80 番、`wss://` は 443 番で TLS を使う。https のページが使えるのは `wss://` だけ（localhost を除く。TLS 1.3 のテーマを参照）。

## フレーム

ハンドシェイクの後、メッセージはすべてフレームで送る。

| ビット | フィールド | 意味 |
|---|---|---|
| 1 | FIN | 1 = メッセージの最後のフレーム |
| 3 | RSV1〜3 | permessage-deflate のような拡張で合意しない限り 0 |
| 4 | Opcode | 0x0 継続、0x1 テキスト、0x2 バイナリー、0x8 Close、0x9 Ping、0xA Pong |
| 1 | MASK | 1 = 4 バイトのマスクキーが続く |
| 7 | Payload length | 0〜125: 長さ。126: 16 ビットの長さが続く。127: 64 ビットの長さが続く |

ブラウザーの `ws.send("Hello")` は `0x81 0x85 0x37 0xfa 0x21 0x3d 0x7f 0x9f 0x4d 0x51 0x58` になる。FIN とテキスト、マスクのビットと長さ 5、マスクキー、マスクしたペイロード。

## マスク

クライアントからのフレームは、TLS の上でもすべて**マスク**する（ペイロードの各バイトを 4 バイトのキーと XOR する）。サーバーからのフレームはマスクしない。キーはフレームの中にあるので、マスクは暗号化ではない。ページのスクリプトが通信路のバイト列を思いどおりに作れないようにするためのもの。そうでないと、WebSocket を理解しないプロキシに、フレームを HTTP の要求に見せかけ、キャッシュを汚染できてしまう。フレームごとに新しい乱数のキーを使う。

## フラグメント、Ping と Pong

メッセージは**フラグメント**に分けられる。最初のフレームは本当の opcode で FIN = 0、続くフレームは継続フレーム（opcode 0x0）、最後は FIN = 1。ページが受け取るのは、それでも 1 つのメッセージ。全体の大きさがわかる前に、送り始められる。

**Ping** と **Pong** は制御フレームで、125 バイト以下、分割しないが、フラグメントの間には入ってよい。Ping を受け取った側は、同じペイロードの Pong で答える。ブラウザーはこれを自分で行い、JavaScript の API では Ping を送れない。どのくらいの間隔で Ping を送り、Pong をどれだけ待つかは、アプリケーションが決める。

## 接続の終了

どちらの側も、ステータスコードを入れた Close フレームで**終了のハンドシェイク**を始められる。相手は自分の Close で答える。その後は通常、サーバーが先に TCP を閉じるので、TIME-WAIT で待つのはサーバー（TCP の接続の終了のテーマを参照）。

| コード | 意味 |
|---|---|
| 1000 | 正常な終了 |
| 1001 | 離れる（サーバーが止まる、ユーザーがページを離れる） |
| 1002 | プロトコルのエラー |
| 1008 | ポリシーの違反 |
| 1009 | メッセージが大きすぎる |
| 1005、1006、1015 | 送らない。手元で起きたことを表す（1006 = Close フレームなしで閉じた） |

ページが `ws.close()` に使えるのは、1000 か 3000〜4999 のコードだけ（コードなしでもよい）。

## Origin とクロスサイト WebSocket ハイジャック

WebSocket には同一オリジンポリシーも CORS もない（CORS のテーマを参照）。ページはどのサーバーにも接続でき、ブラウザーはそのサーバーの Cookie（SameSite で制限されないもの）を送る。ブラウザーはページの `Origin` を付けるので、サーバーはそれを確かめ、知らないオリジンを拒まなければならない（たとえば 403 で）。そうしないと、別のサイトがユーザーのセッションで接続を開けてしまう。これが**クロスサイト WebSocket ハイジャック**（CSWSH）。ブラウザー以外のクライアントは好きな Origin を送れるので、本当の認証（トークンなど）はやはり必要。

## HTTP/2・HTTP/3 の上では

HTTP/2 と HTTP/3 には、101 も Upgrade のヘッダーもない。そこでは WebSocket は、1 つのストリームで `:protocol = websocket` の拡張 CONNECT の要求を使い、200 で答え、Sec-WebSocket-Key と Accept は使わない（RFC 8441、RFC 9220）。

## ステップ実行で見てほしいところ

- サーバーの **Sec-WebSocket-Accept の計算**の表と、**readyState** が CONNECTING から OPEN、CLOSING、CLOSED と進むこと。
- ブラウザーのフレームにだけある **MASK = 1** とマスクキー、長さのバイト（`0x85` = マスクのビット + 5、サーバーからの 100,000 バイトでは `0x7f …`）。
- サーバーが最初の **TCP FIN** を送ること。
- 「もしも…」のオプションで、**誤った Accept**（Close フレームなし、1006）、写真を**フラグメント**で送る場合（message のイベントは 1 回）、**接続が切れる**場合（ブラウザーは OPEN のまま）。
