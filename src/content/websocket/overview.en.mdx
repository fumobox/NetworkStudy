## Why WebSocket

In HTTP the client asks and the server answers. A chat, a live dashboard or a game needs the server to send whenever something happens. Before WebSocket, pages imitated that with requests:

| Approach | Who can send | Connection | Cost per message |
|---|---|---|---|
| Polling | The client asks every few seconds | A request each time | A whole HTTP request, often for nothing |
| Long polling | The server holds the request until there is news | A new request after each answer | A whole HTTP request per message |
| [Server-Sent Events](/themes/server-sent-events) | Only the server, as a stream | One HTTP response that never ends | A few bytes, but one direction only |
| **WebSocket** | Both sides, at any time | One connection kept open | A 2- to 14-byte header |

## The opening handshake

A WebSocket connection starts as an ordinary HTTP/1.1 GET with `Upgrade: websocket` and `Connection: Upgrade`, a random `Sec-WebSocket-Key`, `Sec-WebSocket-Version: 13` and the page’s `Origin`. The server agrees with **101 Switching Protocols**, and from then on the same TCP connection carries WebSocket frames instead of HTTP. Any other status means failure.

The server proves that it understood the request by computing `Sec-WebSocket-Accept`:

```
dGhlIHNhbXBsZSBub25jZQ==                    Sec-WebSocket-Key (as text)
+ 258EAFA5-E914-47DA-95CA-C5AB0DC85B11      a fixed GUID
→ SHA-1 → base64 = s3pPLMBiTxaQ9kYGzzhZRbK+xOo=
```

The browser does the same and fails the connection if the value differs. This is not authentication: it only shows that the server speaks WebSocket and is not an HTTP server tricked into answering. `ws://` uses port 80 and `wss://` uses TLS on port 443; an https page can only use `wss://` (except to localhost; see the TLS 1.3 theme).

## Frames

After the handshake, every message is sent in frames:

| Bits | Field | Meaning |
|---|---|---|
| 1 | FIN | 1 = the last frame of the message |
| 3 | RSV1–3 | 0 unless an extension such as permessage-deflate was agreed |
| 4 | Opcode | 0x0 continuation, 0x1 text, 0x2 binary, 0x8 Close, 0x9 Ping, 0xA Pong |
| 1 | MASK | 1 = a 4-byte masking key follows |
| 7 | Payload length | 0–125: the length; 126: a 16-bit length follows; 127: a 64-bit length follows |

The browser’s `ws.send("Hello")` becomes `0x81 0x85 0x37 0xfa 0x21 0x3d 0x7f 0x9f 0x4d 0x51 0x58`: FIN and text, the mask bit and length 5, the masking key, and the masked payload.

## Masking

Every frame from the client is **masked** (each payload byte XORed with the 4-byte key), even over TLS, and frames from the server never are. Masking is not encryption, since the key is in the frame. It exists so that a script in a page cannot choose the exact bytes on the wire: otherwise it could make a WebSocket frame look like an HTTP request to a proxy that does not understand WebSocket, and poison its cache. Each frame gets a new random key.

## Fragments, Ping and Pong

A message can be split into **fragments**: the first frame has the real opcode and FIN = 0, the following ones are continuation frames (opcode 0x0), and the last has FIN = 1. The page still receives one message. This lets a sender start before it knows the whole size.

**Ping** and **Pong** are control frames: at most 125 bytes, never fragmented, but allowed between fragments. The receiver of a Ping answers with a Pong carrying the same payload; browsers do this by themselves, and the JavaScript API cannot send a Ping. How often to ping and how long to wait for the Pong is up to the application.

## Closing the connection

Either side starts the **closing handshake** with a Close frame carrying a status code; the other side answers with its own Close. The server then normally closes TCP first, so it is the server that waits in TIME-WAIT (see the TCP closing theme).

| Code | Meaning |
|---|---|
| 1000 | Normal closure |
| 1001 | Going away (the server shuts down, or the user leaves the page) |
| 1002 | Protocol error |
| 1008 | Policy violation |
| 1009 | Message too big |
| 1005, 1006, 1015 | Never sent: they describe what happened locally (1006 = closed without a Close frame) |

A page may call `ws.close()` only with 1000, a code from 3000 to 4999, or no code at all.

## Origin and cross-site WebSocket hijacking

WebSocket has no same-origin policy and no CORS (see the CORS theme): a page can connect to any server, and the browser sends that server’s cookies (those that SameSite does not restrict). The browser adds the page’s `Origin`, and the server must check it and refuse unknown origins, for example with 403. Otherwise another site can open a connection with the user’s session: **cross-site WebSocket hijacking** (CSWSH). Clients outside a browser can send any Origin, so real authentication (such as a token) is still needed.

## Over HTTP/2 and HTTP/3

HTTP/2 and HTTP/3 have no 101 and no Upgrade header. There, WebSocket uses an extended CONNECT request with `:protocol = websocket` on one stream, answered with 200, and without Sec-WebSocket-Key and Accept (RFC 8441, RFC 9220).

## What to look for in the walkthrough

- The server’s **Sec-WebSocket-Accept computation** table, and the **readyState** going from CONNECTING to OPEN, CLOSING and CLOSED.
- **MASK = 1** and a masking key only on the browser’s frames, and the length bytes (`0x85` = mask bit + 5, and `0x7f …` for 100,000 bytes from the server).
- The server sending the first **TCP FIN**.
- In “What if…”, a **wrong Accept** (no Close frame, 1006), a photo sent in **fragments** (one message event), and a **lost connection** (the browser still says OPEN).
