## なぜ 4 つのセグメントなのか

TCP の接続は両方の向きにデータを運び、**向きごとに別々に閉じる**。もう送るものがない側が **FIN** を送り、相手が **ACK** で確認応答する。両方の向きを閉じるには、それぞれが FIN と ACK を 1 回ずつ送るので、4 つのセグメントになる。

最初の FIN と ACK の後、接続は**ハーフクローズ**（半分だけ閉じた状態）になる。FIN を送った側はもうデータを送れないが、受け取ることはできる。相手は、自分のアプリケーションも閉じるまで送り続けられる。

SYN と同じように FIN もシーケンス番号を 1 つ消費するので、Seq + 1 で確認応答される。

## 途中の状態

- 先に閉じる側は **FIN-WAIT-1** → **FIN-WAIT-2** → **TIME-WAIT** → CLOSED と進む。
- 相手は **CLOSE-WAIT** → **LAST-ACK** → CLOSED と進む。アプリケーションが接続を閉じるまで CLOSE-WAIT に留まるので、CLOSE-WAIT の接続がたくさん残っているときは、たいていアプリケーションが閉じ忘れている。

## なぜ TIME-WAIT があるのか

最後の ACK を送った側は、接続を忘れる前に TIME-WAIT で **2MSL**（セグメントの最大生存時間の 2 倍。RFC 9293 では MSL は 2 分）待つ。理由は 2 つある。

1. 最後の ACK が失われると、相手は FIN を再送する。TIME-WAIT にいればもう一度確認応答できるが、接続を忘れていたらリセット（RST）を返してしまう。
2. この接続の古いセグメントが遅れて届いても、ネットワークから消えるのを待つことで、同じアドレスとポートを使う新しい接続のセグメントと取り違えないようにする。

## ステップ実行で見てほしいところ

- FIN のたびに **Seq**、**Ack**、**SND.NXT**、**RCV.NXT** が 1 ずつ進むこと。
- 「もしも…」のオプションで、両者が CLOSING を経る**同時クローズ**、**最後の ACK** のロス、TIME-WAIT を経ない RST による**中断**。

## 手元で試す

curl が接続を閉じた後、先に閉じた側である自分の側では、接続がしばらく TIME-WAIT に残る。

```sh
curl -4 -s -o /dev/null https://example.com/ ; sleep 1
netstat -an -p tcp | grep 172.66.147.243
sysctl net.inet.tcp.msl
```

出力（macOS 26、2026-09-29。自分のアドレスは置き換えた。example.com のアドレスは違うことがある）:

```
$ curl -4 -s -o /dev/null https://example.com/ ; sleep 1
$ netstat -an -p tcp | grep 172.66.147.243
tcp4  0  0  192.168.1.10.52257  172.66.147.243.443  TIME_WAIT
$ sysctl net.inet.tcp.msl
net.inet.tcp.msl: 15000
```

- 接続は TIME_WAIT にある（netstat は状態の名前を下線で書く）。30 秒ほどしてもう一度 netstat を実行すると、消えている。macOS の MSL は 15 秒（`15000` ms）なので、TIME-WAIT は 2 × MSL = 30 秒。RFC 9293 が例に挙げる 2 分より短い。
- Linux では `ss -tan state time-wait` で同じものが見える。Linux は TIME-WAIT を 60 秒保つ。Wireshark では、表示フィルター `tcp.flags.fin == 1` で FIN のセグメントが見える。
