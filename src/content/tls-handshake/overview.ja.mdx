## TLS が守るもの

`https://` のページを開くとき、TLS は接続を 3 つの面で守っている。

- **機密性** — ネットワークの途中にいるだれにも、データを読まれない。
- **完全性** — 気づかれずにデータを書き換えられない。
- **認証** — **証明書**によって、クライアントは本物のサーバーと話していると確かめられる。

## 1 往復のハンドシェイク

1. **ClientHello** — クライアントが対応している方式を示し、鍵交換の自分の分（**key share**）も最初から送る。
2. **ServerHello** — サーバーが方式を選び、鍵交換の自分の分を送る。これで両者が同じ秘密を計算し、**ハンドシェイク用の鍵**を導く。この後はすべて暗号化される。
3. **EncryptedExtensions、Certificate、CertificateVerify、Finished** — サーバーが証明書を送り、秘密鍵を持っていることを示し、ハンドシェイクを確認する。
4. **Finished** — クライアントもすべてを確かめて確認する。両者は**アプリケーション用の鍵**に切り替える。

## 証明書と信頼の連鎖

サーバー証明書は**中間 CA** が署名し、中間 CA の証明書は**ルート CA** が署名している。クライアントがルートを信頼するのは、それが自分の**信頼ストア**に最初から入っているときだけ。各証明書の署名と有効期間、サーバー証明書が接続したい名前に対して発行されていること（**SAN**）を確かめる。どれかが不合格なら、クライアントは**アラート**を送って中断する。

## ステップ実行で見てほしいところ

- 図が**暗号化なし**から**暗号化**に切り替わるところ。
- **証明書チェーン**のパネルで、各項目が ✓ や ✗ になっていくところ。
- 「もしも…」のオプションで、期限切れ・名前の不一致・信頼していない CA・中間証明書の欠落が、それぞれどうなるか。

## 手元で試す

`openssl s_client` は TLS のハンドシェイクをして、合意した内容を表示する。OpenSSL（たとえば Homebrew の `openssl@3`）を使う。macOS に入っている `openssl`（`/usr/bin/openssl`）は LibreSSL で、`-brief` も `-verify_hostname` もない。

```sh
openssl s_client -connect example.com:443 -servername example.com -brief < /dev/null
```

出力の一部（macOS 26 の OpenSSL 3.6.1、2026-09-29）:

```
CONNECTION ESTABLISHED
Protocol version: TLSv1.3
Ciphersuite: TLS_AES_256_GCM_SHA384
Peer certificate: CN=example.com
Verification: OK
Negotiated TLS1.3 group: X25519MLKEM768
```

- **Protocol version** と **Ciphersuite** は、ServerHello が選んだもの。**Verification: OK** は、サーバーの証明書チェーンを信頼ストアと照らして確かめたこと。`-servername` は SNI で名前を送るが、証明書がその名前と一致するかを s_client が確かめるのは、`-verify_hostname example.com` も付けたときだけ。
- **group** は、key share に使った鍵交換の方式（グループ）。ここでは X25519MLKEM768 で、X25519 と耐量子の ML-KEM を組み合わせたもの。ステップ実行ではふつうの X25519 を使う。`-brief` を外して `-showcerts` を付けると、チェーン全体を表示する。
- `curl -v https://example.com/` でも、TLS のバージョンと証明書が見える。Wireshark のフィルター `tls.handshake` で読めるのは ClientHello と ServerHello だけ。TLS 1.3 では、ハンドシェイクの残りはもう暗号化されている。
