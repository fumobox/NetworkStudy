## なぜハンドシェイクが必要か

TCP はバイトの並びを、欠けず順番どおりに届ける。そのために、送る側は送るバイトに**シーケンス番号**を振り、受け取る側はどこまで受け取ったかを**確認応答番号**で知らせる。

データを流す前に、両者は自分の番号がどこから始まるかを相手に伝えておく必要がある。この出発点が**初期シーケンス番号**（ISS）で、それを交換するのが 3 ウェイハンドシェイクの役目。

## 3 つのセグメント

1. **SYN** — クライアントが自分の ISS を送る。
2. **SYN, ACK** — サーバーが自分の ISS を送り、クライアントの ISS を確認応答する（SYN 自体がシーケンス番号を 1 つ消費するので、クライアントの ISS + 1）。
3. **ACK** — クライアントがサーバーの ISS を確認応答する。

3 つ目が届くと、両者がお互いの出発点を知った状態になり、接続は **ESTABLISHED** になる。

## ステップ実行で見てほしいところ

- パケットの詳細で、**Seq** と **Ack** がセグメントごとにどう変わるか。
- それぞれの**状態**の変化（クライアントは CLOSED → SYN-SENT → ESTABLISHED、サーバーは LISTEN → SYN-RECEIVED → ESTABLISHED）。
- 「もしも…」のオプションで、セグメントが失われたときに**再送タイマー**が何をするか、閉じたポートが何を返すか。

## 手元で試す

`nc -vz` は TCP の接続を開き、すぐに閉じる。開いているポートと、自分のコンピューターの閉じているポートを試す。

```sh
nc -vz example.com 443
nc -vz 127.0.0.1 9
```

出力（macOS 26、2026-09-29）:

```
Connection to example.com port 443 [tcp/https] succeeded!
nc: connectx to 127.0.0.1 port 9 (tcp) failed: Connection refused
```

- 「succeeded」は、3 ウェイハンドシェイクが終わったこと。「Connection refused」は、相手が SYN にリセットで答えたこと。ステップ実行のポートが閉じている場合と同じく、そのポートで待ち受けているものはない。
- ファイアウォールが SYN を黙って捨てると、nc は待ち続けてタイムアウトになる。ステップ実行の SYN が失われる場合と同じく、SYN は再送される。
- Linux の nc も、少し違う言葉で同じ結果を出す。セグメントそのものを見るには、Wireshark でキャプチャーして、表示フィルター `tcp.flags.syn == 1 || tcp.flags.reset == 1` を使う。Wireshark は既定で、シーケンス番号を最初の番号からの相対値（0 から）で表示する。
