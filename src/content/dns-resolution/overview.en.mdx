## What DNS does

Computers connect to each other by IP address, but people use names like `www.example.com`. DNS (the Domain Name System) turns names into addresses. Nobody holds the whole list: the name space is split into **zones**, and each zone is managed by its own **authoritative servers**.

## Who takes part

- **Stub resolver** — a small client in your PC. It asks one question and waits for the final answer.
- **Full-service resolver** — usually run by your ISP, your company, or a public DNS service. It does the actual work and keeps a **cache**.
- **Root, TLD, and example.com servers** — each is the authoritative server for its own zone. The root knows who runs each top-level domain such as `com.`, the `com.` servers know who runs `example.com.`, and the `example.com.` servers know the answer.

## Recursive and iterative queries

The stub sends a **recursive** query (the RD flag): “please find the answer for me.” The resolver then sends **iterative** queries: each server either answers or **refers** the resolver to a server closer to the answer (NS records, plus their addresses as **glue** when needed).

## Caching and TTL

Every record comes with a **TTL** (time to live). The resolver keeps records until their TTL runs out, so later lookups can skip steps — or skip the servers entirely. Even “this name does not exist” (NXDOMAIN) is cached for a while.

## What to look for in the walkthrough

- The **Flags** in each message: RD on the recursive query, AA on the authoritative answer, and no AA on referrals or cached answers.
- The resolver’s **cache** growing with each referral and answer.
- In the “What if…” options: how a warm cache shortens the path, and what NXDOMAIN, a CNAME, or an unresponsive server look like.

Records on this page are written as `NAME TYPE RDATA TTL` to match the cache table. Tools like `dig` show them as `NAME TTL CLASS TYPE RDATA`.

## Try it yourself

`dig +trace` follows the delegation from the root, one server at a time, as a resolver does:

```sh
dig +trace www.example.com A
```

Trimmed output (macOS 26, 2026-09-29; your results will differ):

```
.                 486140 IN NS a.root-servers.net.
;; Received 945 bytes from 192.0.2.1#53(192.0.2.1)
com.              172800 IN NS a.gtld-servers.net.
;; Received 840 bytes from 2001:500:2f::f#53(f.root-servers.net)
example.com.      172800 IN NS hera.ns.cloudflare.com.
;; Received 363 bytes from 192.12.94.30#53(e.gtld-servers.net)
www.example.com.  300    IN A  104.20.23.154
;; Received 76 bytes from 2a06:98c1:50::ac40:20a2#53(hera.ns.cloudflare.com)
```

- Each block ends with the server that answered. The first is your own resolver (its address is replaced with 192.0.2.1 here), which only tells dig where the root servers are. Then come a root server, a .com server and example.com’s own name server: the same chain as in the walkthrough.
- With `+trace`, dig asks every server itself, iteratively, from your computer. Without it, `dig www.example.com` asks your resolver once; run it twice and the TTL has counted down, because the second answer comes from the cache.
- The same command works on Linux. In Wireshark, the display filter `dns` shows the queries and responses.
