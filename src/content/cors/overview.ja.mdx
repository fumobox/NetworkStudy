## 同じオリジンと、オリジンをまたぐ要求

**オリジン**は URL のスキーム・ホスト・ポートの組。`https://app.example.com` と `https://api.example.com` は別のオリジンになる。ページのスクリプトが応答を読めるのは、ふつうは自分と同じオリジンだけ（**同一オリジンポリシー**）。そうでなければ、訪れたどのサイトでも、利用者の Cookie でメールや銀行のページを読めてしまう。

**CORS**（Cross-Origin Resource Sharing）は、ほかのどのオリジンに応答を読ませてよいかを、サーバーが伝えるしくみ。オリジンをまたぐ要求には、ブラウザーが `Origin` ヘッダーを付け、サーバーは `Access-Control-Allow-Origin` で答える。

## プリフライト

要求によっては、送る前に確かめる。GET・HEAD・POST で、ヘッダーが決まったものだけ（`Content-Type` を付けるなら、フォームの形式か `text/plain`）なら、そのまま送る。それ以外、たとえば `Content-Type: application/json` の POST や独自のヘッダー付きの要求は、先に**プリフライト**が要る。

1. ブラウザーが `OPTIONS` に `Origin`、`Access-Control-Request-Method`、`Access-Control-Request-Headers` を付けて送る。Cookie は付けない。
2. サーバーが `Access-Control-Allow-Origin`、`-Allow-Methods`、`-Allow-Headers` と、必要なら `-Max-Age`（ブラウザーが答えを覚えておいてよい時間）を返す。
3. 答えが許していれば、ブラウザーは本番の要求を送る。

## Cookie と `*`

`Access-Control-Allow-Origin: *` はどのオリジンも許すが、資格情報のない要求に限る。ページが Cookie を送る（`credentials: "include"`）なら、サーバーは正確なオリジンを名指しし、`Access-Control-Allow-Credentials: true` も付ける必要がある。

## CORS がしないこと

CORS を強制するのは**ブラウザー**で、サーバーではない。チェックに通らないと、スクリプトには `TypeError` が返るだけで、理由は開発者ツールのコンソールに出る。プリフライトの要らない要求は、すでにサーバーに届いて処理されているので、CORS は要求からサーバーを守るしくみではない。それは認証や CSRF 対策の役目。

## ステップ実行で見てほしいところ

- すべての要求に付く `Origin` ヘッダーと、返ってくる `Access-Control-*` ヘッダー。
- プリフライトが通ったあとに埋まる**プリフライトのキャッシュ**。
- 「もしも…」のオプションで、ふつうの GET（プリフライトなし）、`*` を返すサーバーと何も返さないサーバー、Cookie を送る場合。

## 手元で試す

curl はブラウザーではない。すべてを送り受け取り、CORS の規則は何も強制しない。それでも、ブラウザーが送るヘッダーを付けて、サーバーの答えを読める。ここでは GitHub の公開の API を使う。

```sh
curl -sI -H 'Origin: https://example.org' https://api.github.com/zen
curl -si -X OPTIONS -H 'Origin: https://example.org' \
  -H 'Access-Control-Request-Method: PUT' \
  -H 'Access-Control-Request-Headers: authorization' https://api.github.com/zen
```

出力の一部（macOS 26、2026-09-29）:

```
$ curl -sI -H 'Origin: https://example.org' https://api.github.com/zen
HTTP/2 200
access-control-allow-origin: *
$ curl -si -X OPTIONS -H 'Origin: https://example.org' \
    -H 'Access-Control-Request-Method: PUT' \
    -H 'Access-Control-Request-Headers: authorization' https://api.github.com/zen
HTTP/2 204
access-control-max-age: 86400
access-control-allow-headers: Authorization, Content-Type, If-Match, …
access-control-allow-methods: GET, POST, PATCH, PUT, DELETE
access-control-allow-origin: *
```

- 1 つ目は単純な要求。`access-control-allow-origin: *` は、どのオリジンのページにも（資格情報なしで）応答を読ませる。
- 2 つ目は、`Authorization` のヘッダーを付けた `PUT` の前にブラウザーが送るプリフライト。204 で許すメソッドとヘッダーを答え、`access-control-max-age: 86400` でブラウザーに答えを最長 1 日キャッシュさせる（ブラウザーには上限がある）。
- ブラウザーでは、開発者ツールの Network のパネルにプリフライトが別の `OPTIONS` の要求として現れ、止められた要求は Console に CORS のエラーとして出る。

## このページについて

ページのオリジンは 1 つだけにした。`Access-Control-Expose-Headers`、リダイレクト、Private Network Access は扱わず、ブラウザーが `Access-Control-Max-Age` に設ける上限も省いた。ヘッダーを読めるよう HTTP は暗号化せずに描いているが、実際は HTTPS の上で送る。
