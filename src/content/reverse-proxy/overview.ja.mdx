## サーバーの前に立つもの

アクセスの多いサイトが 1 台のサーバーで動くことはまずない。ブラウザーがつなぐ先は**リバースプロキシ**で、リバースプロキシは要求をいくつかある**バックエンド**のどれかに転送し、応答を返す。RFC 9110 はこの種の仲介者を**ゲートウェイ**と呼ぶ。ブラウザーからはオリジンサーバーに見えるが、要求を翻訳して内側へ転送する。プロキシが返すエラーが 502 Bad *Gateway* や 504 *Gateway* Timeout という名前なのはこのため。要求をバックエンドに振り分けるのが**負荷分散**（ロードバランシング）で、ふつうは 1 つの製品が両方を担う。例えば nginx、HAProxy、Envoy、クラウドのロードバランサー。

ブラウザーに見えるのはプロキシだけ。バックエンドを足したり外したり再起動したりしても、ブラウザーは気づかない。

## TLS はプロキシで終わる

ふつうは、サイトの証明書と秘密鍵をプロキシが持ち、TLS のハンドシェイクをプロキシが自分で行う（**TLS の終端**）。その奥では、要求は運用者が信頼するネットワークを平文の HTTP で（多くは HTTP/1.1 で）通る。そのためバックエンドが受け取るのは `https` ではなく `http` で（RFC 9112 §3.3）、TCP の相手もブラウザーではなくプロキシになる。`http` の要求をすべてリダイレクトして「https を強制する」アプリは、ブラウザーが何を使ったかをプロキシが伝えなければ、いつまでもリダイレクトを繰り返す。プロキシからバックエンドへの通信を、もう一度暗号化することもできる。

## 誰の要求かをバックエンドに伝える

プロキシは、元の要求を表すフィールドを足す。

- `Forwarded`: 標準のフィールド（RFC 7239）。例えば `for=203.0.113.50;proto=https`。求められたホスト（`host=`）や、プロキシ自身（`by=`）も運べる。
- `X-Forwarded-For`: 広く使われるが、標準ではない。例えば `203.0.113.50`。
- `X-Forwarded-Proto`: 広く使われるが、標準ではない。例えば `https`。

`Forwarded` では、IPv6 のアドレスは [] で囲み、ポート付きのアドレスは引用符で囲む。例えば `for="[2001:db8:cafe::17]:4711"`。途中のプロキシはそれぞれ自分の分を後ろに足すので、並びは左から右へ伸びる。

これらのフィールドは簡単に偽れる。クライアントが自分で `X-Forwarded-For: 192.0.2.99` を送れば、プロキシは本当のアドレスをその後ろに足す。だから信じてよいのは、自分のプロキシが足した値だけ。右から数えるか、いちばん外側のプロキシでフィールドを置き換える。バックエンドは、プロキシのアドレスから来たときだけこれらのフィールドを受け入れるべき。RFC 7239 は、クライアントのアドレスを送ることによるプライバシーの問題も指摘し、既定では難読化した識別子を使うよう勧めている。

## Host、:authority、Via

HTTP/2 では、サイトの名前は `:authority` の疑似ヘッダーにある。プロキシがバックエンドと HTTP/1.1 で話すときは、そこから `Host` を作る（RFC 9113 §8.3.1）。ゲートウェイは、転送する要求に `Via` を付けなければならない（RFC 9110 §7.6.3）。このフィールドには、プロキシが受け取ったメッセージのプロトコルの版と、プロキシの名前を書く。例えば HTTP/2 で届いた要求には `Via: 2.0 proxy1`、HTTP/1.1 のバックエンドから来た応答には `Via: 1.1 proxy1`。実際には、多くのリバースプロキシは既定で Via を付けない。

## 区間ごとのフィールドと接続の使い回し

メッセージではなく、1 つの接続だけに関わるフィールドがある。`Connection`、`Keep-Alive`、`TE`、`Transfer-Encoding`、`Upgrade`、そして `Connection` に並べたフィールド。プロキシはこれらを転送する前に外し（RFC 9110 §7.6.1）、HTTP/2 ではそもそも使えない（RFC 9113 §8.2.2）。

HTTP/1.1 の接続は既定で開いたままなので（RFC 9112 §9.3）、プロキシは各バックエンドへの接続をいくつか持っておき、使い回す。要求ごとの TCP の（場合によっては TLS の）ハンドシェイクが省ける。HTTP/1.1 の接続は一度に 1 つの要求しか運ばず、応答は順番でしか要求と対応づかない（§9.2）。そのため、応答を待っている接続は使い回せない。

## バックエンドの選び方

どう選ぶかは HTTP では決まっていない。よく使われるのは、**ラウンドロビン**（順番に。nginx や HAProxy の既定）、接続の数が最も少ないもの、クライアントのアドレスや URL のハッシュ。重みを付けて、大きなマシンに多く送ることもある。

**スティッキーセッション**は、ブラウザーを毎回同じバックエンドに送る。ふつうはプロキシが設定する Cookie を使う（例えば HAProxy の `cookie SERVERID insert indirect`）。アプリがセッションをメモリーに持つときに役立つ。代わりに負荷が偏り、そのバックエンドが落ちればセッションは失われる。セッションを共有のストアに置けば、どちらの問題も避けられる。

## ヘルスチェック

ヘルスチェックも HTTP の一部ではなく、製品ごとの設定になる。

- **能動的**なヘルスチェックは、各バックエンドを定期的に確かめる。例えば `GET /healthz` を送る。続けて何回か失敗したら外し、続けて何回か成功したら戻す。
- **受動的**なヘルスチェックは、本物の通信での失敗を数える。例えばオープンソースの nginx には受動的なヘルスチェックしかなく、能動的なヘルスチェックは NGINX Plus の機能。

本物の要求が遅くても、能動的なヘルスチェックは通ることがある。`/healthz` はたいてい軽い処理だから。

## バックエンドが失敗したとき

| 何が起きたか | 状態コード | Proxy-Status の error（RFC 9209） |
|---|---|---|
| 接続を拒否された、または応答が終わる前に閉じられた | 502 Bad Gateway | `connection_refused`、`connection_terminated` |
| 使えるバックエンドがない（例えば、すべてがヘルスチェックに落ちた） | 503 Service Unavailable（`Retry-After` を付けることも） | `destination_unavailable` |
| バックエンドが時間内に答えなかった | 504 Gateway Timeout | `connection_timeout`、`http_response_timeout` |

`Proxy-Status` のフィールド（RFC 9209）は、どのプロキシがなぜエラーを返したかを示す。例えば `proxy1; error=connection_terminated`。

失敗した要求を別のバックエンドに送り直してよいのは、メソッドが**べき等**なときだけ。GET、HEAD、PUT、DELETE は繰り返しても安全だが、POST はもう処理されたかもしれない（RFC 9110 §9.2.2）。同じく、504 は要求が失敗したという意味ではなく、どうなったか誰にもわからないという意味。注文はできているかもしれない。

## L4 と L7

| | L7（HTTP） | L4（TCP） |
|---|---|---|
| 振り分ける単位 | 要求ごと | TCP の接続ごと |
| TLS が終わる場所 | プロキシ | バックエンド（パススルー） |
| パス、ヘッダー、Cookie を読めるか | 読める | 読めない |
| Forwarded や Via を足す、キャッシュする | できる | できない |
| 証明書が要る場所 | プロキシ | すべてのバックエンド |

L4 のロードバランサーのほうが単純で速いが、バックエンドに見えるのはロードバランサーのアドレスだけになる。クライアントのアドレスを残すには、ロードバランサーが最初に **PROXY protocol** のヘッダーを送る。`PROXY TCP4 203.0.113.50 192.0.2.10 51514 443` のような 1 行で、RFC ではなく HAProxy の仕様。バックエンドはこれを受け取るよう設定しておかなければならず、受け入れるのはロードバランサーからだけにすべき。そうしないと、クライアントが偽のヘッダーを送れてしまう。ほかに、応答をバックエンドから直接クライアントに返す **DSR**（direct server return）という方法もある。

## 共有キャッシュとしてのプロキシ

リバースプロキシは、応答をすべての利用者のためにキャッシュすることもできる（**共有キャッシュ**、RFC 9111）。HTTP のキャッシュのテーマでは扱わなかった部分。

- `s-maxage` は共有キャッシュにだけ効き、そこでは `max-age` より優先する。`max-age=0, s-maxage=60` なら、プロキシは 60 秒使い回せるが、ブラウザーはすぐに再検証しなければならない。
- `private` は、共有キャッシュが応答を保存してはならないという意味。
- `Authorization` の付いた要求への応答を共有キャッシュが使い回せるのは、`public`、`must-revalidate`、`s-maxage` のどれかがあるときだけ（§3.5）。
- `Age` はキャッシュにあった時間を、`Cache-Status`（RFC 9211）はキャッシュが何をしたかを示す。例えば `proxy1; hit; ttl=40` や `proxy1; fwd=uri-miss; stored`。

共有キャッシュは、要求によって変わる応答に気をつけなければならない。`Vary` は、応答を変える要求のフィールドを示す。キャッシュが見ていないフィールドで応答が変わると、違う利用者にその応答を返してしまう（キャッシュポイズニング）。

## ウォークスルーで見るところ

- 鍵の印がプロキシで止まること。ブラウザーの側は暗号化され、バックエンドの側はされない。
- プロキシが足すフィールド（`Host`、`Forwarded`、`X-Forwarded-*`、`Via`）と外すフィールド（`Removed`）、バックエンドの「アプリから見える値」の表。
- バックエンドの一覧、次に選ぶバックエンド、使い回される接続の表。
- 「もしも…」の選択肢:
  - バックエンドが落ちる: 502、POST を再試行しないこと、ヘルスチェック。
  - バックエンドが遅い: 504。
  - スティッキーセッション。
  - PROXY protocol を使う L4 のロードバランサー。
  - 共有キャッシュ。

## このページについて

- ブラウザーは 1 台、バックエンドは同じ重みの 2 台で、ラウンドロビンで選ぶ。
- ヘルスチェックは 5 秒ごとで、続けて 2 回失敗したら外す。応答を待つのは 30 秒まで。どれも例の値。
- プロキシは `Forwarded` と `X-Forwarded-For` にクライアントの IP アドレスを入れ、`Host` はそのまま渡す。製品によっては既定で書き換える。
- TCP のハンドシェイクと ACK、HTTP/2 の設定は L4 の選択肢でだけ描き、TLS のハンドシェイクは 3 つのメッセージにまとめる（TLS 1.3 のテーマを参照）。
- `Date` は省き、`Age` はプロキシのキャッシュにあった時間だけを数える。ブラウザー自身のキャッシュは描かない。
- バックエンドには説明用のアドレス（RFC 5737）を使う。実際はプライベートアドレスのことが多い。
- PROXY protocol は文字列の版 1 で示す。版 2 はバイナリー。
