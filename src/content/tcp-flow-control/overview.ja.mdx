## なぜ受信側が口を出すのか

TCP は、受け取ったデータを、アプリケーションが読んだときに初めて渡す。それまでデータは受信側の**バッファー**で待つ。送信側が送れるだけ速く送ると、アプリケーションが遅いときにバッファーがあふれてしまう。

そこで受信側が送るセグメントには、どれにも **Window** のフィールドが入っている。Ack の番号から数えて、あと何バイト受け取れるかを表す。これが**フロー制御**で、受信側を守る。ネットワークを守るのは別の役目で、輻輳制御が受け持つ。送信側が送るのは、最大で min(cwnd, 受信ウィンドウ)。

## 送信側のウィンドウ

送信側は 3 つの変数を持つ。

- **SND.UNA**: まだ確認応答されていない最初のバイト。
- **SND.NXT**: 次に送るバイト。
- **SND.WND**: 最後の ACK で知らされたウィンドウ。

ウィンドウは SND.NXT からではなく SND.UNA から始まるので、まだ送れるのは **SND.UNA + SND.WND − SND.NXT** バイト。これが 0 になると、アプリケーションに送るものが残っていても、送信側は止まって ACK を待つ。

## ウィンドウが 0 になったとき

アプリケーションが忙しいと、バッファーが埋まり、受信側はウィンドウ **0** を知らせる。あとでアプリケーションが読むと、受信側は大きなウィンドウの ACK を送る。ところがデータのない ACK は再送されないので、この ACK が失われると、送信側は更新を待ち、受信側はデータを待ち、いつまでも進まない。

これを避けるため、送信側はウィンドウが 0 の間、小さな**ウィンドウプローブ**を、間隔を倍にしながら送り続ける。受信側はプローブのたびに今のウィンドウを返す。

## シリーウィンドウシンドローム（SWS）

受信側が数バイト空いただけでウィンドウを開くと、送信側は小さなセグメントを送ることになり、そのたびに 40 バイトのヘッダーが付く。これを避けるため、受信側は空きが min(バッファーの半分, 1 MSS) 以上になるまでウィンドウを開かない。送信側では、Nagle のアルゴリズム（RFC 896）が、確認応答を待っているデータがある間は小さなセグメントを控える。

## ステップ実行で見てほしいところ

- セグメントを送るたびに**使えるウィンドウ**が減り、ACK のたびにまた増えること。
- **win=0** の ACK、**ウィンドウプローブ**、ウィンドウを開く ACK。
- 「もしも…」のオプションで、**ウィンドウの更新が失われ**次のプローブで回復する場合、**すぐに読む**アプリケーション、**500 バイトずつ読む**アプリケーション（SWS 回避）。
