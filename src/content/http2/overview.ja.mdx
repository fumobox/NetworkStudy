## HTTP/1.1 は 1 つずつ

HTTP/1.1 は TCP の接続を複数の要求に使い回すが、1 つの接続では**要求を 1 つ送り、その応答が全部届くまで待つ**。そのため、大きなファイルがあると、後ろの小さなファイルがみな遅れる。ブラウザーは 1 つのサーバーに 6 本ほどの接続を開いてしのいでいる。また、要求のたびにすべてのヘッダーを文字のまま送る。

## HTTP/2 のストリームとフレーム

HTTP/2 はすべてをバイナリの**フレーム**に分け、要求ごとに**ストリーム**を割り当てる。番号は 1、3、5…（奇数はクライアントが開く）。ストリームの違うフレームを、1 つの接続に**混ぜて**送れる。

| フレーム | 運ぶもの |
|---|---|
| `SETTINGS` | 同時に開けるストリームの数など、接続の上限 |
| `HEADERS` | 要求や応答のヘッダー（HPACK で圧縮） |
| `DATA` | 本文の一部。既定では最大 16,384 バイトで、最後のものに `END_STREAM` が付く |

そのため、小さな `style.css` は大きな `app.js` の後ろで待たない。**HPACK** はヘッダーを短くする。よく使うものは静的テーブルの番号になり、`:authority` のような値は最初の要求のあと動的テーブルに覚えておく。

## ヘッドオブラインブロッキング

それでもすべてのストリームは 1 つの TCP の接続を共有していて、TCP はバイトを必ず順番どおりに渡す。パケットが 1 つ失われると、その後ろに届いた**すべての**ストリームのデータが、再送まで受信バッファーで待つ。これが **TCP のヘッドオブラインブロッキング**。HTTP/3 はストリームが独立した QUIC の上で動き、これを避ける。

## ステップ実行で見てほしいところ

- **要求**の表。ストリームの状態（`half-closed (local)` → `closed`）と、各ファイルがどれだけ届いたか。
- `DATA` フレームの順番。style.css はほかと一緒に要求したのに、最初に届き終わる。
- 「もしも…」のオプションで、比べるための HTTP/1.1 と、パケットのロス（app.js が再送されるまで、TCP の受信バッファーが hero.jpg を止める）。

## 手元で試す

```sh
curl -sI --http1.1 https://example.com/ | head -1
curl -sI https://example.com/ | head -1
```

出力（macOS 26、2026-09-29）:

```
$ curl -sI --http1.1 https://example.com/ | head -1
HTTP/1.1 200 OK
$ curl -sI https://example.com/ | head -1
HTTP/2 200
```

- 同じサーバーが両方を話す。オプションなしなら、curl は TLS のハンドシェイクで ALPN に `h2` を申し出て、サーバーが受け入れる。`curl -v` では `ALPN: curl offers h2,http/1.1` と `ALPN: server accepted h2` の行が見える。
- ブラウザーの開発者ツールでは、Network のパネルに Protocol の列（`h2`、`http/1.1`）を出せる。Wireshark では、表示フィルター `http2` で HTTP/2 のフレームが見えるが、Wireshark が TLS を復号できるとき（たとえばブラウザーの SSLKEYLOGFILE を使う）だけ。

## このページについて

TCP と TLS の接続はすでにできているものとした（HTTP/2 は TLS のハンドシェイクで ALPN により選ぶ）。1 つのメッセージを 1 つのフレームとして描いているが、実際のフレームは複数の TCP セグメントに分かれ、再送されるのは失われたセグメントだけ。HTTP/1.1 の応答も、比べやすいよう同じ大きさに分けて描いた。`WINDOW_UPDATE`、`SETTINGS` への確認応答、`PRIORITY`、`PUSH_PROMISE`、`GOAWAY` は省き、HPACK は表の番号だけを示した。ロスは 1 秒の RTO で回復させている（高速再送は TCP の輻輳制御のテーマで扱う）。
